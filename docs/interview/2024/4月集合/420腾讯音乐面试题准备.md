## 进程、线程区别，进程调度算法，死锁

进程是操作系统进行资源分配的最小单元，线程是操作系统进行运算调度的最小单元。 进程（Process）是计算机中的程序关于某数据集合上的一次运行活动，是系统进行资源分配和调度的基本单位，是操作系统结构的基础。 线程是操作系统能够进行运算调度的最小单位。 它被包含在进程之中，是进程中的实际运作单位。

多线程在宏观上是并行的，在微观上则是分时切换串行的

多进程：适用于CPU密集型
多线程：适用于 I/O密集型的工作场景，这样CPU就会更加合理利用

[参考](https://blog.csdn.net/abcdefg12345666/article/details/111739157)

进程调度算法：
（1）先来先服务
（2）最短作业优先
（3）高响应比优先
（4）最高优先级
（5）时间片轮转
（6）多级反馈队列

死锁：2个或以上的进程在执行过程中，由于竞争资源或彼此通信造成阻塞的现象，此时系统进入死锁状态；
死锁的4个必要条件：（只要发生死锁，这4个条件都满足）
1、互斥条件：一个资源每次只能被一个进程使用；
2、请求与保持条件：一个进程因请求资源而阻塞时，已有的资源不放；
3、不剥夺条件：进程已获得的资源，在完成之前，不能强行剥夺；
4、循环等待条件：若干进程之间形成一种头尾相连的循环等待资源状态；

## 浏览器进程线程

早期浏览器是单进程的，现在chorme是多进程的，浏览器从关闭到打开，有多少进程？
1个浏览器进程，1个GPU进程、1个网络进程、1个渲染进程、现在还有n个插件进程
(1)浏览器进程： 负责控制浏览器除标签页外的界面，包括地址栏、书签、前进后退按钮等，以及负责与其他进程的协调工作，同时提供存储功能
(2)GPU进程：负责整个浏览器界面的渲染。Chrome刚开始发布的时候是没有GPU进程的，而使用GPU的初衷是为了实现3D CSS效果，只是后面网页、Chrome的UI界面都用GPU来绘制，这使GPU成为浏览器普遍的需求，最后Chrome在多进程架构上也引入了GPU进程
(3)网络进程：负责发起和接受网络请求，以前是作为模块运行在浏览器进程一时在面的，后面才独立出来，成为一个单独的进程
(4)插件进程：主要是负责插件的运行，因为插件可能崩溃，所以需要通过插件进程来隔离，以保证插件崩溃也不会对浏览器和页面造成影响
(5)渲染进程：负责控制显示tab标签页内的所有内容，核心任务是将HTML、CSS、JS转为用户可以与之交互的网页，排版引擎Blink和JS引擎V8都是运行在该进程中，默认情况下Chrome会为每个Tab标签页创建一个渲染进程

## 链表、数组、队列的区别和使用场景

数组：构建时必须使用一段连续的空间；增、删、改、查都需要遍历一遍，复杂度是O（n）；但是能直接根据数组下标查找元素
链表：不是连续的，能灵活的分配内存空间；读取要从链表头开始，查询第k个元素的复杂度是O(k)；不适合快速查询；
队列：先进先出，队头：查看和删除数据，队尾：查看和添加数据；适用场景：广度优先搜索

## TCP 和UDP的区别

tcp: 面向连接，全双工，建立连接要用三次握手，断开连接要用4次挥手；传输数据比较慢，但是可靠传输；
udp: 无连接，发送端只管发，接收端只管收，不可靠，实时性高；传输快

## CSP 是什么

为了解决web浏览器安全问题出的一个规范：通过限制 Web 应用程序能够加载和执行的内容，来减少恶意攻击的成功率，主要是看CSP头；

## XSS 和CSRF

都是常见的攻击方式。xss 是跨站脚本攻击，CSRF是跨站请求伪造
xss: 攻击者将脚本嵌入攻击网站，获取用户cookie等信息
csrf: 攻击者诱导用户打开黑客的网站，利用用户的登录状态发起的跨站请求。

## 浏览器渲染机制

浏览器渲染机制：html>dom，css>cssom，最后形成render tree ,最后计算好位置大小和样式，渲染到页面上。
重绘和回流：
回流：页面布局和几何属性需要改变的，比如：宽高、内容、增加、删除
重绘：页面布局和几何属性需要改变的；比如背景，颜色
如何减少重绘和回流：

### CSS

- 使用 `transform` 代替 `top`；
- 使用 `visibility` 替换 `display: none`，前者引起重绘，后者引发回流；
- 避免使用 `table` 布局；
- 尽可能在 `DOM` 树的最末端改变 `class`；
- 避免设置多层内联样式，CSS 选择符从右往左匹配查找，避免节点层级过多；
- 将动画效果应用到 `position` 属性为 `absolute` 或 `fixed` 的元素上，避免影响其他元素的布局；
- 避免使用 `CSS` 表达式，可能会引发回流；
- CSS 硬件加速；

### Javascript
  
- 避免频繁操作样式，修改 `class` 最好；
- 避免频繁操作 `DOM`，合并多次修改为一次；
- 避免频繁读取会引发回流/重绘的属性，将结果缓存；
- 对具有复杂动画的元素使用绝对定位，使它脱离文档流；

## ESmodule 和CommonJS 的区别

其实就是考察的**前端模块化**：前端模块化就是将复杂程序根据规范划分为若干模块，一个模块包括输入、输出。而且模块内部实现是私有的，通过对外暴露接口与其他模块通信，而不是直接调用。
ES module ：ES6 后有的规范，export 导出，import导入；
commonJS: nodejs后有的，module.exports  = A (导出); a = require('./c.js') 导入

Commonjs
1、可以动态加载语句，代码发生在：运行时；
2、混合导出，不用声明前面对象；
3、导出值是拷贝，可以修改导出的值，这在代码出错时，不好排查引入变量污染

ESModule
1、是静态的，不可以动态导出加载语句，只能声明在该文件的最顶部，代码发生在：编译时；
2、混合导出；单个导出，默认导出，互不影响
3、引用值之前都存在映射关系，并且值都是可读的，不能修改；
**CommonJS 模块输出的是一个值的拷贝，ES6 模块输出的是值的引用**

模块化优点：
（1）避免命名冲突
（2）更好的分离模块，按需加载
（3）高复用性
（4）高维护性

### AMD、CMD、CommonJS、ESmodule

AMD(require.js): 异步模块定义；采用异步方式加载模块，模块的加载不影响后续语句的执行。所有依赖这个模块的语句，都定义在一个回调函数中，等到加载完成之后，这个回调函数才会运行。浏览器环境要从服务器端加载模块，这时就必须采用非同步模式，因此浏览器端一般采用AMD规范。
CMD(sea.js): CMD是另一种js模块化方案，它与AMD很类似，不同点在于：AMD推崇依赖前置、提前执行，CMD推崇依赖就近、延迟执行。此规范其实是在sea.js推广过程中产生的。
Commonjs:CommonJS用同步的方式加载模块。在服务端，模块文件都存放在本地磁盘，读取非常快，所以这样做不会有问题。但是在浏览器端，限于网络原因，更合理的方案是使用异步加载。用在服务端；
ESmodule: 常用在客户端

## 箭头函数和普通函数的区别

箭头函数没有自己的this，继承的是当前环境里的this，所以也不能用bind\apply、call 绑定this值
箭头函数更方便适用；
箭头函数不能用作构造函数，使用new，因为没有对应的prototype；
箭头函数没有自己的arguments,因此函数内部无法访问函数的参数列表

### 普通函数和箭头函数的this 指向问题
普通函数看“谁调用我”；箭头函数看“我写在哪”。

场景	普通函数	箭头函数
是否有自己的 this	有	没有
this 由谁决定	调用方式	定义位置
能否被 call/apply/bind 改变	可以	不可以
适合做对象方法	适合	不适合
适合做回调	看情况	很适合
能否作为构造函数 new	可以	不可以

```javascript
import Vue from 'vue';

function hiddenNoMainUser(el: HTMLElement, _binding: any, vnode: any) {
    const getIsMainUser = vnode.context.$store.getters.getIsMainUser;

    if (!getIsMainUser) {
        el.style.display = 'none';
    }
}

const install = {
    componentUpdated: hiddenNoMainUser,
    install: function() {
        Vue.directive('hiddenNoMainUser', hiddenNoMainUser);
    },
};

export default install;

```

## Composition API 和Options API 区别以及好处是什么

vue3 语法糖的script setup  好处：
[官网解释](https://cn.vuejs.org/api/sfc-script-setup.html)

1、逻辑组织方面
options API：碎片化，太多逻辑后难以理解+查找逻辑麻烦
composition API ：分块化，将某个逻辑关注点相关的代码全都放在一个函数里，这样当需要修改一个功能时，就不再需要在文件中跳来跳去
2、逻辑复用方面
options API: 适用混入，mixin ，但是mixin多的时候，会有命名冲突和数据来源不清晰的情况；
composition API 则不会

3、Composition会有更好的类型推断；tree-shaking 友好；减少了this指向不明的情况
